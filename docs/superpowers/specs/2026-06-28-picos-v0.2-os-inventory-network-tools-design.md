# picos v0.2 OS Inventory and Network Tools Design

## Goal

Make `picos` feel more like a small terminal OS by expanding it from a network dashboard into a local system console. The v0.2 milestone should let a developer open `picos`, inspect the current OS and hardware state, run common network reachability checks, and clearly see which actions are read-only, user-level, admin-level, or locked.

## Scope

v0.2 focuses on read-first system visibility and safe network tools.

Included:

- Full system inventory for `picos info --full`.
- TUI workspaces for System, Hardware, Storage, Processes, and Network Tools.
- Better `ping` behavior with configurable count and timeout.
- A safe TCP connect check, exposed as `picos connect <host> <port>`, instead of an interactive telnet shell.
- Permission and privilege status shown in CLI and TUI output.
- Documentation updates for README, CHANGELOG, CODEX, CLAUDE, and HARNESS.

Deferred to the next milestone:

- DOS-style file manager and shell commands such as `dir`, `cd`, `type`, `copy`, `move`, and `edit`.
- Rich document editing beyond basic future text/Markdown support.
- Any default-enabled OS mutation such as changing routes, flushing DNS, disabling interfaces, killing processes, or deleting files.
- Background daemons and plugin execution.

## User Experience

`picos info --full` prints a structured report:

- System: OS name, version, kernel/release, architecture, hostname, uptime, current user, shell, privilege status.
- Hardware: CPU model, CPU count, total memory, free memory, machine model when available.
- Storage: filesystem entries, mount points, size, used/free capacity when available.
- Network: interfaces, DNS servers, gateway, routes summary when available.
- Runtime: Bun/Node versions, picos version, config path.

The TUI gains OS-like workspaces:

- Dashboard: compact health overview.
- System: operating system and runtime facts.
- Hardware: CPU and memory.
- Storage: mounted volumes and capacity.
- Processes: read-only process snapshot.
- Network Tools: ping, TCP connect, DNS, routes, ports, and connections.
- Actions: permission-aware command catalog.

The UI should remain keyboard-driven. Navigation keeps the current workspace model, and nested tool lists require explicit focus before `j/k` moves child items.

## Architecture

New and updated core modules:

- `core/system.ts`: returns normalized OS/runtime/system facts.
- `core/hardware.ts`: returns CPU and memory facts using Bun/Node APIs and safe OS adapters where needed.
- `core/storage.ts`: returns cross-platform volume and filesystem summaries.
- `core/processes.ts`: returns a bounded read-only process snapshot.
- `core/networkTools.ts`: owns ping option validation and TCP connect checks.
- `core/permissions.ts`: reports current user/admin capability where it can be detected safely.
- `core/types.ts`: holds shared inventory/tool result types.

Adapters remain the only place for OS command differences:

- macOS: `sw_vers`, `uname`, `df`, `ps`, `netstat`/`lsof` where available.
- Linux: `/etc/os-release`, `uname`, `df`, `ps`, `ss`/`netstat` where available.
- Windows: PowerShell or native commands for OS caption/version, logical disks, processes, and network data.

All command execution continues through `safeExec()`. Core modules parse adapter results and expose structured data. CLI and TUI only call core APIs.

## Network Tool Design

`picos ping <host>` supports:

- `--count <n>` with a safe bounded range.
- `--timeout <ms>` with a safe bounded range.
- Host validation that rejects shell metacharacters and option-like hosts.
- Clear status: success, timeout, DNS failure, command unavailable, or invalid input where detectable.

`picos connect <host> <port>` supports:

- TCP connect reachability without shelling into telnet.
- Safe host and port validation.
- Timeout support.
- Structured output showing host, port, reachable state, elapsed time, and error message.

Interactive telnet is not part of v0.2 because it creates terminal ownership and credential risks. A future `terminal session` feature can revisit interactive tools behind an explicit sandbox/permission model.

## Permission Model

Every action surfaced in v0.2 has metadata:

- Risk: `read`, `write`, or `destructive`.
- Privilege: `none`, `user`, or `admin`.
- Enabled state.
- Confirmation requirement.
- Adapter ownership.

Read-only inventory and network checks are enabled by default. Write/destructive OS actions remain locked unless they have preview, confirmation, and privilege handling.

## Error Handling

System inventory should degrade gracefully. Missing OS commands or restricted permissions produce partial reports with warnings, not crashes.

Network tools should distinguish:

- Invalid user input.
- DNS/resolve failures where available.
- Timeout.
- Command unavailable.
- Permission denied.
- Unknown execution failure.

The TUI event log records failures and partial-data warnings.

## Testing

Unit tests:

- System inventory normalizes mocked platform data.
- Storage parsers handle macOS/Linux/Windows-like output.
- Process parser caps output and tolerates missing fields.
- Ping command builder validates count, timeout, and host safety.
- TCP connect validates host/port and handles success/failure with injected connectors.
- Permission metadata defaults keep write/destructive actions locked.

Integration/smoke:

- `bun run verify` remains the main quality gate.
- Smoke stays read-only and deterministic.
- Network-dependent commands are documented as local manual checks unless made stable enough for CI.

Manual TUI checks:

- Resize terminal horizontally and vertically.
- Navigate System, Hardware, Storage, Processes, and Network Tools.
- Run ping and TCP connect actions.
- Confirm locked write/destructive actions cannot run accidentally.

## Acceptance Criteria

- `picos info --full` works on macOS, Linux, and Windows with partial-data fallback.
- TUI exposes System, Hardware, Storage, Processes, and Network Tools panels.
- `picos ping <host> --count <n> --timeout <ms>` validates inputs and runs safely.
- `picos connect <host> <port>` performs a TCP reachability check without invoking a shell.
- All OS command execution goes through `safeExec()`.
- Write and destructive actions remain locked by default.
- `bun run verify` passes.
